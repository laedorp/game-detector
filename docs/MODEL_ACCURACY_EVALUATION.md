# Player model accuracy and dataset limits

The detector is a **player-appearance detector**, not an opponent-identity
classifier. FORT-Cuh v1 uses inconsistent full-player class names; preparation
maps those to `player` and excludes `head`, `body`, `ally`, and `Yourself`.
Appearance alone cannot prove that a visible skin is an enemy rather than the
local avatar or an ally. Runtime self filtering and independent clone-game
recordings remain necessary.

## Why the supplied split scores are not final evidence

The original Roboflow assignments are not source independent. The base audit
finds 41 conservative filename-derived source groups spanning 655 images across
splits, including 26 video sequences spanning 616 images. There are no
exact-byte duplicates, but adjacent frames and Roboflow variants still make
the original split metrics optimistic.

`scripts/build_strict_fort_eval.py` can remove known filename-group overlap.
On the released 416 v1 checkpoint those conservative subsets measured:

| Split | Images | Boxes | Precision | Recall | mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|---:|---:|
| Validation | 462 | 614 | 0.746 | 0.665 | 0.710 | 0.350 |
| Test | 253 | 384 | 0.765 | 0.663 | 0.751 | 0.375 |

These remain filename-based development measurements, not unseen-gameplay
claims.

Bucket height is the normalized ground-truth box height projected onto a
1,080-pixel-tall reference frame.

| Split | <=32 px | 33-64 px | 65-96 px | >96 px |
|---|---:|---:|---:|---:|
| Train | 14 | 149 | 297 | 3,417 |
| Validation | 1 | 41 | 44 | 574 |
| Test | 4 | 26 | 14 | 405 |

Validation far examples are distributed across capture-session (17), numbered
sequence (6), video-sequence (1), and isolated original-file (18) groups. All
30 test boxes at <=64 px come from isolated `original_file` groups; test far
scores therefore do not measure held-out gameplay sequences and must not be a

uncertainty intervals.

## Checkpoint-screening evaluator

`scripts/evaluate_fort_model.py` screens local PyTorch checkpoints with
Ultralytics validation. It reports aggregate precision, recall, mAP50,
mAP50-95, and timing. For every size bucket it also emits:

- raw ground-truth total, detected true positives, missed false negatives,
  prediction count, and false positives at confidence 0.25 and 0.45;
- a literal `detected/total` value, precision, recall, and Wilson 95% intervals;
- the full confidence-ranked precision-recall curve;
- 101-point interpolated AP50; and
- a deterministic 500-resample, image-level bootstrap AP50 interval.

The evaluator fails if its custom validator is not captured, if processed image
count differs from the manifest, or if summed bucket targets differ from the
contract box count. Raw counts must always accompany rates.

This is checkpoint screening, not exact static deployment-artifact evaluation.
Ultralytics batches validation images by aspect ratio while `imgsz` is a scalar.
Every final ONNX/OpenVINO candidate still needs a separate evaluator that runs
the application preprocessing and detector on every image at the exact static
height x width, maps detections back to source coordinates, and computes the
same aggregate and bucket evidence. Rectangular and detail-pass support is
present in this source checkout, but remains experimental, disabled by default,
and is not a release claim.

### Exact runtime-artifact and centered-detail evaluation

`scripts/evaluate_fort_runtime_model.py` evaluates one static ONNX or OpenVINO
artifact through the application's batch-one BGR preprocessing, selected runtime
backend, decoder, and source-coordinate mapping. The centered detail path is off
by default. Supplying `--detail-crop-size` runs the same static model first on the
full frame and then on a centered source ROI with that requested width; its
height is derived from the model's static H:W aspect ratio and clamped to the
source. A redundant ROI identical to the source is disabled. It invokes the production
`detection.detail_pass.merge_cross_pass_detections` exactly once per applied
detail frame, including the same one-to-one cross-pass IoU rule and unmatched
small-detail limit.

Detail evaluation is deliberately validation-only. The command rejects
`--detail-crop-size` with `--split test` before artifact, dataset, detector, or
image loading; the already-consumed v9 test split must not be used to choose the
detail crop or merge behavior. A typical development comparison is:

```bash
.venv/bin/python scripts/evaluate_fort_runtime_model.py \
  --model path/to/player-384x640.onnx \
  --data datasets/fort_cuh_player_grouped_v9/fort_cuh_grouped.yaml \
  --output runs/runtime-eval/player-384x640-detail768-val \
  --backend onnxruntime --device CUDA --require-full-provider \
  --inference-size 384x640 --split val --detail-crop-size 768
```

The atomically published record hashes every deployment-artifact member,
dataset contract and metadata file, the evaluator, and the exact preprocessing,
detail merge, decoder, and detector sources. Configured-pipeline metrics include
aggregate and projected-height-bucket raw detected/total, misses, predictions,
false positives, AP50/PR, and deterministic image-level bootstrap intervals. A
detail run also reports the unmerged full-frame primary with the identical metric
schema, so the A/B shares the exact artifact, runtime, images, and process.
Primary timings remain separate; detail preprocess, inference, and postprocess
are reported independently, detail postprocess includes the cross-pass merge,
and total runtime-pipeline timing spans both passes while excluding decode.
These validation results can rank candidates but still require a new independent
holdout, reviewed negative scenes, and physical target-GPU latency qualification.

Runtime-evaluation schema 4 also writes compact paired evidence for every exact
contract member at each declared confidence threshold. It stores only a stable
member digest and per-size-bucket target/true-positive/false-positive counts;
filenames, pixels, boxes, and prediction coordinates are omitted. Compare two
reports (or the primary and configured detail pipelines from one report) with:

```bash
.venv-export/bin/python scripts/compare_fort_runtime_evaluations.py \
  --baseline runs/runtime-eval/baseline-val/metrics.json \
  --candidate runs/runtime-eval/candidate-val/metrics.json \
  --output runs/runtime-comparison/baseline-vs-candidate
```

The comparator requires identical dataset membership, evaluator/matching
policy, and confidence operating point; recomputes aggregate consistency from
the paired rows; and reports deterministic paired image-bootstrap intervals for
recall and false-positive deltas. Its advancement policy is deliberately
development-only. A pass is available only at the app's confidence 0.25,
with exactly 2,000 paired image-level resamples, at least 30 genuine 33-64px
targets spread across at least 30 distinct images and 15 privacy-safe grouped
source clusters, an absolute far-recall gain of at least 10 points whose image
and source-group cluster-bootstrap lower bounds are both above zero, no added far
false positives, and no aggregate precision or recall regression over one
point. Group identities come from the dataset's conservative filename/session
and perceptual-union heuristic; they improve uncertainty accounting but do not
prove real-world scene independence. Even a passing comparison always records
`release_qualification.qualified=false`; independent gameplay holdout,
reviewed negative scenes, and exact frozen target-GPU latency remain mandatory.

### Adopt a development-selected candidate without approving release

The launcher, PyInstaller spec, build identity, and release-asset validator read
the same self-hashed `models/RELEASE-DEFAULT.json` pointer. Model filenames,
static dimensions, and the optional detail ROI's requested source width are not
duplicated in those components (`0` disables the detail pass). The checked-in
pointer continues to select the existing 416 model until an operator explicitly
promotes a different candidate; merely exporting or evaluating a candidate does
not change the application.

First run the adoption command in read-only mode with the exact winner runtime
report and the complete sealed fixed-tournament selection directory:

```bash
.venv-export/bin/python scripts/adopt_fort_release_candidate.py \
  --candidate runs/release-candidates/player-384x640 \
  --candidate-evaluation runs/runtime-eval/player-384x640-val/metrics.json \
  --tournament-selection runs/model-tournament/development-selection \
  --validate-only
```

The command reruns the candidate export validator, including ONNX/OpenVINO
parity; validates the selection manifest's canonical self-hash, current
orchestrator/comparator/exporter/evaluator identities, all seven hash-bound
comparison records, and a replay of the fixed bracket; and rejects any staged
candidate other than its exact winner. Validation does not trust declared
outcome booleans: it reruns the pinned comparator at confidence `0.25` with
exactly `2,000` samples for all seven bracket edges from the four sealed runtime
reports, requires byte-identical canonical output, and derives the winner
again. It also strict-parses the canonical sealed plan and cross-checks its
dataset, runtime, four portable candidate/report paths, and n/s initial weights
against the selection. The winner's candidate-content,
candidate-manifest, ONNX, runtime-model-content, report, output-head, static
NCHW, dataset, and pipeline identities must all agree. A configured winner
binds the tournament plan's positive detail ROI width into the pointer; a
primary winner binds `0`. Neither can be changed independently during adoption.
The tournament manifest and `ADOPTION.json` both bind the lowercase SHA-256 of
`utils/public_evidence.py`; semantic pointer validation requires that pair to
match the exact scanner imported by the release contract. Adoption snapshots
the scanner with its other source inputs through the final publication boundary.
The final independent-holdout protocol evaluates whichever exact workload won:
one rectangular primary pass when the pointer binds `0`, or rectangular
primary plus the production detail pass when it binds a positive width.

Only after reviewing the read-only result, repeat without `--validate-only`.
The command copies both ONNX and OpenVINO formats, labels, attribution, a safe
adoption record, path-redacted candidate/training/winner receipts, exact
training results, the sealed tournament manifest, all seven exact comparisons,
and the tournament's sealed plan, four runtime reports, and two n/s training
results into a new content-addressed
`models/release-defaults/<candidate-content-sha256>/` directory. The canonical
receipts retain the exact original local-record hashes, model/dataset/checkpoint
hashes, training parameters and versions, epoch/result counts, selected output
head, static shape, and selected runtime metrics without publishing workstation
paths or platform identity strings. The pointer binds an exact role, size, and
SHA-256 for every member; the selection manifest cross-links its sealed inputs
and winner report.

The selected scale's sealed training-results bytes must exactly equal the
staged winner's packaged `training-results.csv`. Adoption requires the pinned
Ultralytics results columns, finite numeric values, a contiguous epoch sequence,
and row/epoch counts matching the candidate training contract. Its adoption
record includes a false-qualified replay receipt binding the sealed plan, seven
recomputed comparisons, derived winner, and selected training-results identity.
Absolute/file paths are rejected in JSON values and keys and in CSV text; only
portable relative logical paths and ordinary public HTTP(S) references survive.

Adoption verifies the entire existing release SHA manifest, appends the new
members atomically, and atomically replaces `RELEASE-DEFAULT.json` last.
Existing model bytes are never overwritten or deleted. Every adoption, pointer,
and receipt keeps `approved`, model-accuracy, independent-holdout, frozen-build,
and target-GPU qualification false. Adoption only makes the candidate the
default for the remaining gates; it cannot authorize a release. First build and
measure the exact frozen pointer workload on every claimed target GPU. Consume
the one-time independent holdout only after that workload passes its
performance-eligibility gate, then run reviewed negatives and the remaining
release checks.

A genuinely fresh launcher profile uses the complete pointer workload. Choosing
the Recommended detector again (or resetting its model tier to Recommended)
also applies that workload. Existing saved profiles retain their explicit detail
setting during migration and are not silently opted into a newly selected second
pass; to opt in, explicitly reselect the Recommended detector and review the
shown requested ROI width before starting.

### Fixed n/s deployment tournament

After both audited training runs are complete, stage two exports from each
`best.pt`: one `end2end` and one `traditional`, all at static `384x640`. Run
`scripts/evaluate_fort_runtime_model.py` once per ONNX export on validation with
the same device/provider requirements and the same nonzero
`--detail-crop-size`. Each report must therefore contain both the configured
center-detail result and its full-frame primary reference. Do not run the
tournament against `test`; the orchestrator rejects test reports and has no
override.

Record the four sealed candidate directories and runtime reports in canonical
sorted JSON with one trailing newline. Paths must be portable relative paths
from the plan file; absolute paths, drive prefixes, backslashes, and traversal
are rejected. Replace every placeholder before running it:

```bash

  --output runs/model-tournament/development-selection
```

The orchestrator revalidates the completed-run provenance packaged into every
candidate, every artifact hash, the exact current exporter/evaluator/pipeline
source identities, ONNX/report binding, dataset identity, shape, head, provider
request, and primary/detail evidence. It then invokes the paired comparator at
exactly confidence 0.25 with 2,000 resamples. At least 30 far targets across 30
images and 15 grouped-dataset source groups are evidence prerequisites; both
image-level and source-group bootstrap samples must retain far ground truth.

The bracket order is intentionally not configurable:

1. Detail challenges primary separately for every n/s and head combination.
2. Traditional challenges end-to-end within n and within s, using the pipeline
   selected in step 1.
3. The surviving s configuration challenges the surviving n configuration.

A challenger advances only when the comparator's entire development policy
passes. Failure to improve keeps the incumbent; missing or inconsistent
evidence aborts the tournament. The seven comparisons and
`selection-manifest.json` appear together through one no-replace atomic
directory publication, so a partial bracket is never a selection result. The
manifest always says `release_qualification.qualified=false` and records that
no test split was consumed. Its winner may proceed to the new independent
holdout, reviewed negatives, and physical frozen-build GPU gates; it is not a
release-model approval.

## Exact independent runtime evidence after adoption

The sealed COCO package is not compatible with, and must never be converted
into, the grouped-v9 `val`/`test` semantics. After the development tournament
selects one candidate and `scripts/adopt_fort_release_candidate.py` installs its
content-addressed assets, use
`scripts/evaluate_independent_holdout_runtime.py`. Its `plan` command binds the
dynamic adopted model/labels, candidate-manifest hash, exporter/adoption and
the self-contained path-redacted candidate/training/winner-runtime receipts and
tournament evidence copied into the release directory. That evidence includes
the exact sealed plan, four runtime reports, two n/s training-results files,
selection manifest, and seven comparison records. The plan also binds
rectangular HxW, exact
exported output head, explicit GPU provider, centered model-aspect detail ROI,
confidence points, latency limit,
and complete frozen decision rule before sealed member access.
The workload must exactly match the adopted tournament winner: detail width `0`
runs primary-only, while a configured winner uses its exact positive production
detail width. The independent run cannot retune or reverse that choice.

Before spending the sealed one-time holdout, the provisionally adopted exact
workload must first pass latency and compatibility on the physical target GPU
and frozen build. This run order prevents a too-slow winner from wasting the
holdout; it does not turn those prerequisite results into release approval.

The `evaluate` command then runs the sealed normalized COCO boxes through the
exact batch-one application path. Every workload uses the rectangular
full-frame primary and source-coordinate postprocessing. A configured winner
also runs the same static artifact on the centered model-aspect detail ROI and
performs one production cross-pass merge; a primary winner does not. The frozen
scalar detail setting is the maximum source ROI width, and production derives
the applied height from the exact static model H:W. It fails closed on development packages,
underfilled 33-64/65-96/>96 inventories, fewer than 1,000 reviewed negatives,
negative inventory mismatches, square or changed artifacts, CPU/partial GPU
execution, provider/shape/output drift, a completely redundant configured detail pass,
partial image/target coverage, input mutation, or an existing evidence path.
Release eligibility additionally requires at least 15 independent capture
sessions overall, 15 target-bearing sessions in each gating bucket, and 15
sessions contributing reviewed negatives, so one recording cannot dominate the
raw target count.

Final evidence contains raw detected/total and false-positive counts at 0.25
and 0.45, reviewed-negative false positives, primary-versus-detail reference
metrics, synchronous primary/detail/end-to-end timing, deterministic image
bootstrap intervals, and capture-session cluster intervals. <=32px target
recall/misses are descriptive only, but every unmatched prediction across all
sizes contributes to aggregate release precision. Atomic evidence publication precedes the single
evidence-SHA-bound consumption record and immediate retirement. The `verify`
command recomputes the frozen-rule result and verifies the exact plan,
candidate, report bytes, and retired ledger chain.

Only the exact repository-owned `proaim-independent-holdout-v1` decision rule
and policy hash can set `canonical_release_policy_matched=true`; custom CLI
thresholds remain diagnostic and cannot become release-eligible by passing or
by recomputing a receipt self-hash. The portable publication inventory is fixed
to the receipt, metrics, plan, both ledger events, and a self-hashed artifact
manifest. Its evaluator, holdout, privacy-helper, and application-pipeline
source hashes are pinned. A protected workflow must still authenticate the run
origin and pre-access plan commitment—self-hashes alone are not authenticity.

Even a passing result is only
`verified_release_eligible_evidence_not_release_approved`. The evaluator never
changes the release-default pointer or marks model accuracy, physical target
GPU, frozen build, independent holdout, legal redistribution, or overall
release approval true. Those decisions stay in the separate manual release
workflow.
